# 앱과 포트 점검하기

[첫 실습](01-shell.md)에서 연 Ubuntu 셸을 사용한다. 앱을 기동할 때는 계정, 키 파일, 로그 디렉토리가 준비되어 있어야 한다. 매분 실행되는 `monitor.sh`는 이미 실행 중인 앱을 찾아 점검한다.

## 누가 실행하고 무엇을 읽을 수 있을까?

```bash
id -nG
ls -ld "$AGENT_HOME/upload_files" "$AGENT_HOME/api_keys"
```

첫 명령은 내 그룹 이름을 보여준다. 두 번째 명령의 `-d`는 디렉토리 자체의 권한을 보여준다. 세 계정이 파일을 공유하는 `upload_files`의 그룹은 `agent-common`이다. 키를 보관하는 `api_keys`의 그룹은 운영·개발 계정만 속한 `agent-core`다. `AGENT_HOME`은 로그인할 때 설정된 앱의 기본 경로다.

## 프로그램이 실행 중일까?

```bash
pgrep -x agent-app-linux
```

실행 중인 프로그램 하나를 **프로세스**, 그 번호를 **PID**라고 한다. `pgrep -x`는 이름이 정확히 일치하는 프로세스들의 번호를 출력한다. 실습 앱은 부모와 자식 프로세스가 있어 숫자가 두 개 나올 수 있다. 코드의 `find_app_pid`는 큰 PID부터 보면서 이미 종료된 프로세스를 건너뛰고 하나를 출력한다.

## 앱이 연결을 기다리는 포트가 있을까?

```bash
port=15034
ss -H -ltn "sport = :$port"
```

**포트**는 한 컴퓨터 안에서 어느 서비스에 연결할지를 정하는 번호다. 결과에 `LISTEN`과 `0.0.0.0:15034`가 보이면 그 번호에서 TCP 연결을 기다리는 소켓이 있다. 스크립트의 `check_port`는 이 조회 결과가 비어 있으면 오류를 낸다. 별도로 방화벽은 **밖에서 들어오는 연결을 허용할지** 정한다. 실습에서는 SSH 접속용 20022번과 앱용 15034번을 허용했다.

포트 점검이 사용하는 조건문을 직접 읽어 보자.

```bash
listener="$(ss -H -ltn "sport = :$port")"
if [[ -z "$listener" ]]; then
    echo "기다리는 소켓이 없습니다"
else
    echo "포트에서 연결을 기다립니다"
fi
```

`-z`는 문자열이 비어 있는지 검사한다. 조건이 참이면 `then` 아래, 거짓이면 `else` 아래를 실행하고 `fi`에서 끝낸다. 실습 앱이 떠 있으면 두 번째 문구가 나온다.

## 실패하면 어디까지 실행할까?

```bash
APP_PROCESS=no-such-proc "$AGENT_HOME/bin/monitor.sh"
echo "$?"
```

첫 줄 맨 앞의 `이름=값`은 그 명령을 실행하는 동안에만 점검 대상을 바꾼다. 앱은 계속 동작한다. 화면에 `[ERROR] Process 'no-such-proc' is not running`이 나오고, 바로 다음 줄은 `1`을 출력한다. `$?`는 직전 명령의 **종료 코드**다. 정상 완료는 0이고, 이 스크립트는 대상 프로세스 또는 포트가 없으면 1로 끝나므로 그 회차의 로그도 쓰지 않는다.

코드에서 `명령 || fail "..."`은 왼쪽 명령이 실패하면 오른쪽의 오류 처리 함수를 실행한다는 뜻이다. 다음은 두 점검을 통과한 뒤 [자원 사용률을 읽는 단계](03-resources.md)다.
