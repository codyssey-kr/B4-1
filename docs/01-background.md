# 배경지식

이 과제에서는 서버에 접속할 계정을 정하고, 계정별 접근 권한을 설정한 뒤, 앱 상태를 매분 기록한다.

```text
접속 통제        SSH 포트 변경, Root 차단, 방화벽
권한 분리        계정, 그룹, 파일 권한, ACL
실행 환경        환경 변수, 일반 계정 실행, 프로세스, 포트
상태 관측        CPU, 메모리, 디스크, 헬스 체크
기록과 자동화    로그 포맷, 로그 교체, cron
```

## 1. 위협 모델과 SSH

**위협 모델**은 누가, 무엇을, 어떤 경로로 공격하는지 정리하고 그에 맞는 방어를 고르는 사고방식이다.

| 위협 | 방어 | 효과와 한계 |
|---|---|---|
| 22번 포트 자동 스캔과 무차별 대입 | 포트를 20022로 변경 | 자동화된 시도를 줄인다. 포트 스캔으로 찾을 수 있어 단독 방어는 아니다. |
| 이름이 알려진 `root` 계정 공격 | `PermitRootLogin no` | 공격자가 계정 이름부터 알아내야 하고, 침입해도 권한 상승 단계가 남는다. |
| 불필요하게 열린 서비스 | 방화벽 기본 차단 | 허용한 포트 외의 접근 경로를 없앤다. |
| 계정 탈취 후 피해 확산 | 최소 권한 | 탈취된 계정이 접근할 수 있는 범위를 제한한다. |

Root 직접 접속을 막으면 작업자가 자기 계정으로 접속한 뒤 권한을 올리므로, **누가 작업했는지 추적**하기도 쉬워진다.

### sshd 설정에서 알아둘 점

- 설정 파일은 `/etc/ssh/sshd_config`이고, 대부분의 지시어는 처음 읽은 값을 사용한다. `Port`는 여러 줄을 지정할 수 있으므로 `sshd -T` 출력의 모든 `port` 줄을 확인한다. [OpenSSH 설정 매뉴얼](https://man.openbsd.org/sshd_config#Port)
- `/etc/ssh/sshd_config.d/*.conf`가 먼저 포함될 수 있으므로 실제 적용값은 `sshd -T`로 확인한다.
- `sshd -t`는 설정 문법을 검사한다. 재시작 전에 실행해야 접속이 끊기는 사고를 막는다.
- Ubuntu 22.10 이후에는 소켓 활성화를 사용해 포트 변경 절차가 다를 수 있다. 이 실습에서는 Ubuntu 22.04 컨테이너에서 `service ssh restart`로 변경을 적용했다.

### 원격 서버에서 안전한 변경 순서

```text
1. 방화벽에서 새 포트 허용
2. sshd -t로 설정 검사
3. sshd 재시작(기존 접속은 유지)
4. 새 터미널에서 새 포트로 접속 확인
5. 기존 포트 차단
```

순서를 바꾸면 서버에 다시 접속하지 못할 수 있다.

## 2. 방화벽

방화벽은 들어오고 나가는 패킷을 규칙에 따라 허용하거나 차단한다. **UFW**는 리눅스 커널의 패킷 필터를 쉽게 설정하는 도구다.

```sh
ufw default deny incoming    # 들어오는 연결은 기본 차단
ufw default allow outgoing   # 나가는 연결은 기본 허용
ufw allow 20022/tcp          # SSH
ufw allow 15034/tcp          # 앱
ufw enable
ufw status verbose
```

- **허용 목록 방식**: 모두 막고 필요한 것만 열면, 실수로 띄운 서비스도 외부에 노출되지 않는다.
- **상태 추적**: 내부에서 시작한 연결의 응답은 인바운드 규칙을 따로 열지 않아도 돌아온다.
- **LISTEN과 방화벽은 별개**: 방화벽이 막아도 프로그램은 LISTEN 상태일 수 있다. `ss`는 프로그램 상태를, `ufw status`는 접근 정책을 보여준다.
- **Docker 주의**: 호스트에서 `-p`로 공개한 컨테이너 포트는 호스트 UFW 규칙을 우회할 수 있다. 이 과제는 컨테이너 내부에서 UFW를 실행했다.

## 3. 계정, 그룹, 권한

### 최소 권한 원칙

각 계정에 **업무에 필요한 최소한의 권한만** 준다. 개인이 아니라 역할에 권한을 주면 구성원이 바뀌어도 그룹 소속만 조정하면 된다.

| 계정 | 역할 | agent-common | agent-core |
|---|---|---|---|
| agent-admin | 운영, cron 실행 | O | O |
| agent-dev | 개발, 스크립트 작성 | O | O |
| agent-test | QA | O | X |

그룹 변경은 **새 로그인 세션부터** 적용된다.

### rwx의 의미는 파일과 디렉토리에서 다르다

| 권한 | 파일 | 디렉토리 |
|---|---|---|
| `r` (4) | 내용 읽기 | 안의 이름 목록 보기 |
| `w` (2) | 내용 수정 | 파일 생성, 삭제, 이름 변경(`x`도 필요) |
| `x` (1) | 실행 | 안으로 들어가거나 통과하기 |

`750`은 소유자 `rwx`, 그룹 `r-x`, 기타 `---`이다.

- 경로의 파일에 접근하려면 **모든 상위 디렉토리에 `x`**가 필요하다. 그래서 `/home/agent-admin`에 구성원용 통과 권한을 줬다.
- Bash 스크립트는 해석기가 내용을 읽어야 하므로 경로로 직접 실행할 때 파일의 읽기·실행 권한이 모두 필요하다. `bash 파일명`으로 읽어 실행할 때는 파일의 읽기 권한이 필요하다.

### setgid 디렉토리

`chmod 2770`의 맨 앞 `2`가 setgid다. 디렉토리에 설정하면 안에서 만든 파일이 **디렉토리의 그룹을 상속**해, 공유 디렉토리의 파일 그룹이 작성자 개인 그룹으로 흩어지지 않는다.

### ACL

기본 권한은 소유자, 그룹 하나, 기타만 표현한다. **ACL**은 특정 사용자나 그룹별 권한을 추가한다.

```sh
setfacl -m g:agent-core:rwx DIR      # 현재 디렉토리 권한
setfacl -d -m g:agent-core:rwx DIR   # 새로 만들 파일이 상속할 기본 권한
getfacl DIR                          # 확인
```

- `ls -l`의 권한 끝에 있는 `+`는 ACL이 설정되었다는 표시다.
- `mask`는 소유 그룹과 이름을 지정한 사용자·그룹 항목의 최대 권한이다. `group:x:rwx`여도 mask가 `r--`면 실제 권한은 `r--`다.
- 새 파일은 부모 디렉토리의 기본 ACL을 상속하되, 프로그램이 생성할 때 요청한 모드가 권한의 상한이 된다. 예를 들어 일반 파일을 `0666`으로 생성하면 상속된 ACL에 실행 비트가 있어도 파일에 실행 권한이 생기지 않는다. [Linux ACL 매뉴얼](https://man7.org/linux/man-pages/man5/acl.5.html)

## 4. 환경 변수와 실행 환경

환경 변수는 프로세스에 전달되는 이름과 값의 쌍이다. 코드를 고치지 않고 경로와 포트 같은 설정을 바꿀 수 있고, 값을 고정해 실행 결과를 재현할 수 있다.

| 위치 | 적용 범위 |
|---|---|
| `export NAME=value` | 현재 셸과 그 자식 프로세스 |
| `~/.bashrc` | 해당 사용자의 대화형 셸 |
| `/etc/profile.d/*.sh` | 모든 사용자의 로그인 셸 |
| crontab 상단 | 해당 crontab의 작업 |

`su - user`는 로그인 셸이라 `/etc/profile.d`를 읽지만, **cron은 이 파일들을 읽지 않는다.** 이 차이가 "직접 실행하면 되는데 cron에서는 안 되는" 문제의 흔한 원인이다.

**일반 계정으로 앱을 실행하는 이유**는 앱에 취약점이 있어도 공격자가 얻는 권한을 그 계정으로 제한하기 위해서다.

## 5. 프로세스와 포트

### 프로세스

프로세스는 실행 중인 프로그램이며 고유한 PID를 가진다.

| 상태 | 의미 |
|---|---|
| `R` / `S` | 실행 중 / 대기 중 |
| `D` | 중단할 수 없는 대기(주로 디스크 I/O) |
| `Z` | 좀비. 종료했지만 부모가 회수하지 않아 목록에만 남음 |

```sh
pgrep -x NAME   # 프로세스 이름이 정확히 일치
pgrep -f TEXT   # 명령줄 전체에서 문자열 검색
```

- 이 컨테이너에서 `pgrep -x`가 비교하는 이름(`comm`)은 최대 15바이트다. `agent-app-linux-arm64`는 `agent-app-linux`로 보인다.
- `pgrep -f`는 그 문자열이 들어간 셸 명령까지 찾아 오탐을 낼 수 있다.
- 좀비는 `pgrep`에 잡히지만 실제로 동작하지 않으므로 헬스 체크에서 제외해야 한다.

### 포트와 LISTEN

포트는 한 서버에서 여러 네트워크 서비스를 구분하는 번호다. 서버 프로그램이 포트에서 연결을 기다리는 상태가 **LISTEN**이다.

```sh
ss -ltn                      # TCP LISTEN 소켓을 숫자로 표시
ss -ltnp                     # 프로세스 정보까지 표시
ss -H -ltn 'sport = :15034'  # 헤더 없이 특정 포트만 조회
```

| 바인딩 주소 | 접근 가능 범위 |
|---|---|
| `0.0.0.0` | 모든 IPv4 네트워크 인터페이스 |
| `127.0.0.1` | 같은 시스템 내부 |

## 6. 셸 스크립트

### 종료 코드

모든 명령은 끝날 때 숫자를 반환한다. `0`은 성공, 그 외는 실패이며 직전 값은 `$?`로 확인한다. 호출한 셸이나 CI는 이 값으로 성공 여부를 판단할 수 있다. 이 과제의 매분 cron 작업은 표준 출력과 오류를 버리므로 점검 실패 시 자동 알림은 발생하지 않는다.

### 리다이렉션

| 기호 | 동작 |
|---|---|
| `>` | 파일을 비우고 새로 쓴다 |
| `>>` | 파일 끝에 추가한다 |
| `2>&1` | 표준 오류를 표준 출력과 같은 곳으로 보낸다 |
| `>/dev/null` | 출력을 버린다 |

로그에 `>`를 쓰면 실행할 때마다 이전 기록이 사라지므로 `>>`를 사용한다.

### 자주 쓰는 문법

- `"$VAR"`: 값에 공백이 있어도 하나의 인자로 전달하도록 항상 따옴표로 감싼다.
- `${VAR:-default}`: 값이 없을 때 기본값을 사용한다.
- `$(command)`: 명령의 출력을 값으로 사용한다.
- `set -u`: 정의되지 않은 변수를 오류로 처리한다.
- Bash 산술은 **정수만** 지원하므로 소수 비교에는 `awk`를 사용한다.

## 7. 자원 사용률 계산

### CPU

`/proc/stat`의 값은 부팅 후 **누적 시간**이므로, 현재 사용률을 알려면 두 시점의 차이를 구한다.

```text
전체 증가량 = 두 시점의 CPU 시간 합계 차이
유휴 증가량 = 두 시점의 idle + iowait 차이
사용률(%)  = (전체 증가량 - 유휴 증가량) / 전체 증가량 × 100
```

코어가 18개인 환경에서 한 코어를 100% 쓰면 전체 사용률은 약 5.6%다.

### 메모리

```text
사용률(%) = (MemTotal - MemAvailable) / MemTotal × 100
```

리눅스는 남는 메모리를 디스크 캐시로 활용하므로 `MemFree`는 실제 여유보다 작게 보인다. `MemAvailable`은 회수 가능한 캐시까지 고려한 값이다.

### 디스크

`df -P /`의 `Use%`를 사용한다. `-P`는 장치 이름이 길어도 한 줄 출력을 유지해 파싱이 안정적이다.

### 컨테이너에서의 차이

일반적인 컨테이너의 `/proc/stat`과 `/proc/meminfo`는 컨테이너 제한이 아니라 **호스트(VM) 전체 값**을 보여준다.

## 8. 로그 설계와 보존

좋은 운영 로그는 **언제, 무엇이, 어떤 값이었는지**를 기계가 읽을 수 있는 일정한 형식으로 남긴다.

```text
[2026-11-19 03:09:02] PID:6133 CPU:0.1% MEM:5.2% DISK_USED:3%
```

- 고정 포맷이면 `grep`, `awk`로 집계할 수 있다.
- 시간순으로 누적되어 장애 전후의 변화를 비교할 수 있다.

### 로그 교체

로그를 그대로 두면 디스크를 가득 채워 서비스 장애로 이어진다. **로그 교체**는 파일이 커지면 새 파일로 바꾸고 오래된 파일을 삭제한다.

```text
monitor.log.8 → monitor.log.9 (기존 .9 삭제)
monitor.log.1 → monitor.log.2
monitor.log   → monitor.log.1
새 monitor.log 생성
```

| 방식 | 장점 | 단점 |
|---|---|---|
| logrotate | 표준 도구, 압축 등 기능이 풍부 | 보통 하루 주기로 실행되어 크기 제한을 넘을 수 있음 |
| 스크립트 구현 | 기록 시점마다 크기를 정확히 검사 | 직접 구현하고 시험해야 함 |

여러 프로세스가 동시에 로그를 교체하면 파일이 꼬일 수 있어 `flock`으로 잠근다.

## 9. cron

cron은 정해진 시각에 명령을 실행하는 서비스다.

```text
┌ 분(0-59)
│ ┌ 시(0-23)
│ │ ┌ 일(1-31)
│ │ │ ┌ 월(1-12)
│ │ │ │ ┌ 요일(0-7)
* * * * * 명령
```

```sh
crontab -e             # 현재 사용자 작업 편집
crontab -l             # 현재 사용자 작업 확인
crontab -u USER -l     # root가 특정 사용자 작업 확인
```

cron 환경은 로그인 셸과 달리 최소한으로 구성된다. 기본 `PATH`가 `/usr/bin:/bin`이고 사용자의 프로필도 읽지 않으므로, **절대 경로를 쓰고 필요한 값을 스크립트에 지정**한다.

## 10. 실습 환경의 격리

| 환경 | 네트워크 격리 | 특징 |
|---|---|---|
| VM | 독립된 OS와 커널 | 실제 서버와 가장 가깝지만 무겁다. |
| 컨테이너 | 자체 네트워크 네임스페이스 | 가볍고, 커널은 호스트와 공유한다. |
| WSL2 배포판 | 이전 실습에서 배포판 간 방화벽 간섭을 관찰 | 격리 범위는 WSL 네트워크 설정에 따라 확인해야 한다. |

컨테이너는 보통 systemd 없이 실행되므로 `service`로 서비스를 시작하고, 방화벽을 사용하려면 `NET_ADMIN` 권한이 필요하다. 컨테이너를 재시작하면 프로세스와 방화벽 규칙을 다시 올려야 한다.
